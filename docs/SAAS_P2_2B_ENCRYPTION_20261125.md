# P2.2b — scoped authenticated credential and backup encryption

Base main a184f1f (merged PR #27). Offline candidate; existing roadmap acceptance and personal deployment unchanged.

Uses cryptography AES-256-GCM, random 96-bit nonce per encryption and authenticated header binding format, scope, record and key ID. Separate generated 256-bit keys for each MAX capsule, Telegram bot identity and backup epoch; separate private key directory required. Private regular files, no symlinks/hardlinks, bounded reads and atomic fsynced envelope publication. New encrypted credential install refuses overwrite, MAX encrypted mode rejects coexistence with legacy max.json, no plaintext fallback. Explicit opt-in key path integrated with worker secret loader, provisioning, isolated MaxClient factory and restored cohort gate. Gateway composition can explicitly load its encrypted bot token instead of a raw token argument (mutually exclusive). No automatic migration of existing secrets. Rotation uses a distinct new scoped key, verifies before/after atomic replacement, retains both key files; neither automatic key destruction nor messenger-token rotation is performed. Trusted operator must stop the affected runtime before rotation and control all key-file writes. Keys themselves are private plaintext files, not KMS/HSM-backed, and must be separately retained. Runtime necessarily holds decrypted credentials in memory. IPC keys remain separate existing files; no key zeroization or protection against root/host compromise.

Encrypted backup accepts only the latest clean anchored standalone delivery snapshot, checks exact content digests again during packaging, authenticates epoch/generation and encrypted member set. Bounded prototype: 32 MiB aggregate snapshot data, 64 MiB envelope plaintext maximum, memory-based packaging; no plaintext archive file, but source snapshot and restored private destination are plaintext and must be protected by storage encryption. No deletion of source snapshots. Restore decrypts to new private staging directory, verifies independent anchor and SQLite integrity before publishing; stale/dirty anchor, wrong key, tamper and existing destination fail closed. Backup-key rotation preserves data and old key retention, not rollback proof for the key files themselves. Anchor still needs independent durable storage and trusted exclusive host orchestration. No browser profile encryption or online database encryption, no cross-host migration, no actual account data. Production requires encrypted volume/backup storage, external key custody and revocation/rotation procedure, appropriate bounds/streaming for larger snapshots, deployment-boundary enforcement and live acceptance.
