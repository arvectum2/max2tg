# P2.2b — resumable trusted onboarding

Base: main 2aa55cb (PR #13). Offline development only; P2.2b remains open.

`SharedOnboarding` reserves one external shared capsule for a trusted, already authenticated actor and forum using a stable opaque request ID. Account/capsule/owner/route/request metadata is one SQLite transaction. Repeating the same request returns the same capsule; actor/forum conflicts and existing owners are refused. Failed transactions may leave empty private layout directories, not active accounts. No raw MAX credential is accepted at the gateway.

Stages: RESERVED -> FORUM_VERIFIED -> PROVISIONED -> ACTIVE; REVOKED is terminal. Injected Bot API reads verify exact forum, supergroup/forum flags, no public username or linked chat, actor creator, bot administrator with topic rights, and two members. Bot identity is pinned to the verified request and checked at gateway startup. These are point-in-time observations, not proof that a forum cannot later gain members or that the caller really is authenticated; the caller must be a trusted operator. No public endpoint, user-facing flow, new Telegram group or invite creation. Verification failures prevent activation; active memberships are not continuously policed by this slice. No live Bot API calls in tests.

`worker_provision.py` validates three distinct private worker directories and local MAX-only secret schema/identity, and publishes ACL and IPC key files atomically without overwriting existing content. Repeating identical provisioning is safe; conflicting identity/key or missing secret fails closed. Local preparation holds the worker lock; the verification callback is trusted provisioning evidence, not an attestation against a compromised host. Interrupted preparation before ACL publication can resume with the same key. Gateway activation requires fresh forum verification and provision evidence; it is desired state, not proof of authorization or healthy worker. Revocation atomically disables the route and desired state, preserving data; connecting revocation to container shutdown and dynamic gateway channel management remains open.

Both existing Docker integration tests now use this onboarding path for two synthetic users, with separate read-only MAX secret volumes and actual isolated runtime, then supervised crash/recovery and UNKNOWN quarantine. 825 tests passed, targeted Ruff, runtime preflight, unchanged Spec Kit structural gate, isolated Docker and supervised bridge smoke passed. 33 existing PTB warnings. No real credentials, account, personal bridge, network policy or deployment modified.

Next: operational activation/deactivation reconciliation between onboarding desired state, gateway channels and supervisor, with safe dynamic channel lifecycle, then controlled live-network design, user authorization flow and isolated account acceptance. Secret rotation/encryption, history and media parity remain open. Do not lift production shared-mode guard.
