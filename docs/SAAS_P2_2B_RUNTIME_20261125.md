# P2.2b — isolated shared gateway and worker lifecycle

Base: ffe9e94 (merged PR #8). Date: 2026-11-25. Offline candidate only. P2.2b remains open; P2.2c and production SaaS acceptance are not established.

## Implemented

- `SharedGatewayRuntime`: explicit injected Bot API transport, per-registry OS lock, bot-identity-pinned polling checkpoint, strict topic-scoped IPC, separate poll and drain loops, cancellation and ordered shutdown. Authorized updates and the next polling offset commit atomically in FULL SQLite before the next getUpdates call. A storage error rolls back the entire batch and offset. Unknown dispatch on cancellation remains UNKNOWN. Unsupported authorized or unbound updates are retained BLOCKED; unauthorized group/private updates are not stored. Legacy unscoped egress cannot fall back to General in this runtime.
- `SharedWorkerRuntime`: private worker lock, injected MAX transport, lifecycle, read-only route lookup and local mapping refresh, private durable ingress and egress ledgers, receipt mapping repair, bounded gap journal for unsupported/unbound/paused/unverified self events. Verified echoes only; unverified self-originated messages are held for review rather than forwarded. No Telegram bot token is required in worker environment. Worker receives authenticated IPC and checks its trusted topic map before send.
- Trusted gateway-only topic creation records SENDING before a single create_forum_topic call. Confirmed positive topic ID plus owner/forum route recheck permits binding; timeout/invalid response becomes UNKNOWN, revocation BLOCKED. No automatic repeat of ambiguous creation. Topic creation is an explicitly invoked gateway operation; automatic discovery/provisioning from MAX is not yet implemented.
- Runtime locks allow stale socket removal only after a connection-refused probe and inode check. IPC stops listening, cancels/joins active handlers before closing journals, with bounded receive time. Existing dedicated personal runtime and supervisor shared-mode guard remain unchanged.

Tests run against temporary owner-private roots and fake MAX/Bot API boundaries, not real accounts. Full suite 811 passed; focused 53 passed; targeted Ruff, runtime preflight, and unchanged Spec Kit structural gate passed. 33 existing PTB deprecation warnings. No live MAX/TG operation, service change, or destructive physical test performed.

## Remaining gates

Same host/UID process separation is not an OS security boundary: workers still access the local registry, and per-tenant filesystem/secret isolation must be enforced by a separate deployment architecture before real untrusted tenant operation. No production entrypoint or supervisor enabling yet. Gateway loop stops on polling/storage error; restart orchestration and long-idle Telegram update-ID epoch reconciliation need review (do not blindly reset offsets or start a second poller). Private onboarding/control commands are outside this prototype. Real MAX listener history/catch-up and persistent cursors, recovery of gap events, durable unsupported mutations, browser-originated self messages, media and replies remain incomplete; no automatic replay of gap/UNKNOWN events. Automatic MAX chat discovery and topic provisioning, per-tenant diagnostics, quota/retention/encryption and actual isolated two-account acceptance remain open. Actual OS-level network/disk fault tests remain deferred. Keep personal bridge untouched.

Next: isolate worker runtime secrets and routes from the central registry; then add supervised start/stop and catch-up on a separate authorized test environment. P2.2c requires independent MAX and Telegram test accounts and the original field acceptance evidence.
