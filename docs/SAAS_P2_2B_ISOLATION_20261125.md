# P2.2b — isolated tenant channels and Linux container boundary

Base: 09bb37f (merged PR #9). Offline candidate only. P2.2b remains open; P2.2c and production SaaS acceptance are not established.

## Implemented

- `IsolatedWorkerRuntime` accepts only its own state folder, IPC channel, key, forum/actor IDs and injected MAX client. It has no registry/plane instance and does not read central SQLite or other tenants' credentials. Signed nonce-bound route queries return only the channel's own active topic bindings. Missing or mismatched route fails closed; unavailable route queries record a gap instead of guessing a destination. Ingress refreshes the trusted routes before MAX delivery. Existing legacy same-UID prototype remains compatible.
- `SharedGatewayRuntime(channels=...)` takes explicit separate per-session channel directories. It rejects overlap with central registry or other channels and verifies directory ownership/mode. Each egress listener is bound to one session identity and uses that session's central key; a valid key from another channel cannot query routes or enqueue. Central egress independently verifies the active forum/topic before send. Gateway-to-worker IPC uses the dedicated channel and worker-local ACL. No global registry mount in the isolated worker.
- Docker smoke creates five disposable named volumes, uses an existing image, read-only app/test mounts, isolated network, non-root UID 65532, dropped capabilities, no-new-privileges, memory/PID limits, no Docker socket. Two actual worker containers see only their own state and channel volumes. The gateway container sees only its registry and both channels, not worker state volumes. Initialization uses synthetic credentials and a disposable provisioning container. There is no public port, external network or real messenger call. The test checks active network interfaces/IPv4 routes rather than assuming Linux exposes no down tunnel devices. All resources are removed and label-filtered absence verified. CI repeats this test using the freshly built image.

## Evidence

813 local tests passed, targeted Ruff, runtime preflight, immutable Spec Kit structural gate passed (33 existing PTB warnings). Two new in-process tests exercise wrong channel and identity, topic revocation, registry-directory rejection, exact forum delivery and receipt return. Actual Mac mini Docker Linux test passed with three separate runtime containers, two tenant-bound outgoing messages and two confirmed incoming messages, no duplicates, no central/other-worker state mounts. First network assertion was overly strict on Docker Desktop due to down kernel tunnel interfaces; corrected to check active interfaces and IPv4 routes, rerun passed. This is a synthetic deployment topology test, not a security penetration test or real account acceptance.

## Remaining gates

Central legacy registry still stores MAX credential files; only the worker's *access* to central/other tenants' secrets is removed in this slice. Production must move MAX credentials to per-worker secret storage, keep only routing metadata and per-channel keys at the gateway, securely provision/rotate keys, enforce mounts and restricted outbound network access. Separate per-tenant volumes and read-only container root protect only against the tested access paths, not a compromised host, orchestrator, kernel or arbitrary container escape. A worker can disrupt its own shared channel, so resource quotas and lifecycle recovery are still needed. No real shared worker entrypoint or automatic supervisor activation, catch-up, media/reply/formatting or browser-self-message implementation. No production credential/state migration, launchd restart or change to the personal bridge. Preserve original roadmap criteria; do not enable real shared accounts before separate approved field acceptance.

Next: remove MAX credentials from gateway storage via explicit secret provisioning, then supervised container lifecycle with health, crash recovery and safe per-tenant network policy.
