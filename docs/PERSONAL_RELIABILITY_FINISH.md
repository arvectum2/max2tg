# MAX2TG Personal Reliability — завершающие задачи, срез 2026-10-23

## 1. Постоянная очередь Telegram → MAX: текст, ответы и медиа — готово

`app/tg_outbox.py`: отдельная SQLite WAL/FULL очередь
`~/.local/state/max2tg/tg-outbound.sqlite3`, права 0600.
Уникальный ключ (Telegram group ID, message ID), безопасное
сравнение payload SHA-256, состояние RECEIVED → SENDING →
SENT/UNKNOWN/FAILED. Исходный текст, форматирование и ссылка reply
фиксируются до MAX RPC.

Подтверждённый MAX ID сохраняется в SQLite до TopicStore mapping;
при рестарте повреждённый/отставший mapping восстанавливается из
подтверждённых записей. После reconnect фоновый процесс досылает
ТОЛЬКО достоверно неотправленные RECEIVED. При таймауте/сбое во время
запроса исход UNKNOWN — слепого повторного MAX SEND_MESSAGE нет.
При паузе чата очередь не трогается. Нет обещания exactly-once:
MAX WebSocket не предоставляет доказанной идемпотентности запросов.

Медиа: в SQLite до сети записывается Telegram file_id, тип, имя,
MIME и размер, затем file.get_file() и upload в MAX выполняются
отдельным этапом ПЕРЕД отправкой chat SEND_MESSAGE. Подготовленный
MAX attach сохраняется в колонке prepared и может использоваться при
безопасном восстановлении до отправки. Сбой скачивания/загрузки ещё
не является отправкой сообщения в MAX, поэтому отмечается FAILED;
таймаут уже вызванного SEND_MESSAGE остаётся UNKNOWN и НЕ повторяется.
Есть лимит 25 МБ на вложение, чтобы не скачивать гигантские файлы
в память. Реальный Telegram Bot API может иметь более низкий лимит
скачивания; это повод показать FAILED и предложить меньший файл.

Открытый подпункт: отдельная постоянная очередь для исходящих
TG edits/reactions (пока прямые RPC, без безопасного автоматического
повтора); физическая приёмка реальных Telegram-файлов в изолированном
тестовом чате, где MAX обработка файла может завершиться по-разному.

## 2. Редактирование составных MAX-сообщений — частично готово

Для нескольких подтверждённых `send_message` частей, созданных
нашим ботом, поддерживается последовательная идемпотентная замена
всех частей. Если новый текст короче — остаточные продолжения
получают явную отметку, а не оставляют устаревший текст. При
неоднозначной ошибке edits могут быть повторены как идемпотентные.
Если новая версия длиннее ранее разосланной и потребовала бы
дополнительных частей, операция остаётся BLOCKED.
Медиаальбомы и несопоставленные сообщения не изменяются.

В живой SQLite прежняя BLOCKED правка имеет текст длиной 49 символов,
но НЕТ подтверждённой Telegram outbox части, созданной ботом.
Автоматически разблокировать её нельзя — иначе есть риск изменить
чужое сообщение. Она остаётся BLOCKED, пока владелец явно не
отметит как REVIEWED.

## 3. Диагностика из Telegram — готово

`/status`: сводка MAX, Telegram, обеих очередей и изменений.
`/issues`: только администратор, список проблем без содержимого
сообщений, идентификаторов собеседников и токенов вложений.
`/issue_ack <12 hex>`: только для одной BLOCKED mutation,
явно переводит в REVIEWED, НЕ в APPLIED; не делает сетевых запросов.
UNKNOWN/FAILED нельзя автоматически повторять или признавать
доставленными без независимой сверки.

## 4. Восстановление из резервных копий — сухая проверка готова

`scripts/verify_backup_restore.py` копирует SQLite через backup API,
проверяет integrity_check, восстанавливает TopicStore/SQLite в
удаляемом временном закрытом каталоге и сверяет темы, mappings,
курсоры и состояние обеих очередей. Рабочие файлы НЕ заменяются,
служба НЕ перезапускается. Отдельные тесты проверяют порчу
базы и попытку использовать симлинк.

## 5. Физическая приёмка — ещё не закрыта

Нужны отдельные тестовые MAX + Telegram аккаунты. Нельзя
насильно разлогинивать действующий MAX на Mac mini и отключать
сетевой канал/SSD текущего пользователя. План:
- отдельный вход/выход в MAX и авторизация после SMS;
- MAX→TG и TG→MAX (текст/медиа/редакция/длинные сообщения);
- запуск/остановка одного тестового worker, временная потеря сети,
  Telegram timeout и MAX reconnect;
- сравнение счётчиков и идентификаторов, отсутствие дублей;
- проверка полного восстановления из копии тестового состояния.

Текущие результаты — автоматические тесты и изолированный dry-run
восстановления; это НЕ физические испытания диска/сети.

Следующая итерация: очередь edits/reactions, затем P0.5b на
изолированной тестовой MAX-сессии; только после неё Personal Maintenance.


## Завершение Personal — Maintenance

Добавлен `app/tg_mutation_outbox.py`: устойчивый журнал
правок и реакций Telegram→MAX в `tg-mutations.sqlite3`.
До сетевого вызова создаётся запись RECEIVED, перед вызовом SENDING,
после подтверждения SENT. При неопределённом ответе/краше — UNKNOWN,
автоматических повторов нет. Сводка доступна в /status и /issues.
Автоматическая догрузка edits/reactions намеренно выключена:
без внешнего подтверждения нельзя гарантировать отсутствие
побочных эффектов повторного RPC.

Отдельный тестовый MAX-аккаунт отсутствует. Физические испытания
отключений, логаута и поведения протокола остаются **непроведёнными,
а не успешно пройденными**. По решению владельца закрываем
персональную дорожную карту с этим документированным риском,
а выявленные в реальной эксплуатации проблемы устраняем по факту.
Не переводим UNKNOWN в SENT и не выполняем опасные массовые повторы.
