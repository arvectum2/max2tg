# P2.2b — receipt continuity and dependency crash recovery

Base main 11440f9 (merged PR #20). Offline candidate only; P2.2b remains open.

Worker egress now durably records submission_attempted before the first enqueue, even if the IPC response is lost. A signed MISSING after any attempt or ACCEPTED is UNKNOWN, never re-enqueued. Existing pre-migration pending rows lack proof of non-submission and are conservatively marked attempted; newly staged rows start at zero. A failure before the gateway actually commits may therefore require operator reconciliation; this sacrifices some availability rather than risk duplicates. Signed status_verified binds the source key, existing route check and expected text SHA-256; conflicting text returns CONFLICT and is quarantined, never interpreted as a receipt. Legacy status remains for existing diagnostic callers; workers use verified status. Repeated enqueue of an already SENT identical event returns its durable Telegram ID. All terminal worker rows remain terminal. Four regression cases cover accepted/lost-ACK central record disappearance, content mismatch and duplicate enqueue receipt, legacy pending migration. These tests deliberately remove synthetic central rows, never production records.

Extended four-container actual-client TLS test: A loses its dedicated MAX channel, B delivers, A's next update stays RECEIVED. At a known durable queue boundary the test harness hard-kills gateway and entire broker, leaving both workers running; both lose MAX authorization. Restart broker with retained synthetic evidence and stale socket cleanup, then restart gateway with the same volumes and fresh verification. A's queued update is delivered; both workers retain the same IDs and one launch each. The post-send lost receipt scenario remains UNKNOWN across reconnection. Exact synthetic side-effect evidence: four confirmed MAX sends, two confirmed Telegram sends, one uncertain MAX send with exactly one attempt, no duplicates. All disposable resources removed. This is a controlled test harness restart, not automatic production dependency supervision. Hard kill was at a deliberate quiescent queue boundary; arbitrary in-flight gateway crash and coordinated backup/restore acceptance are not proven by this test.

872 tests passed, targeted Ruff, runtime preflight and unchanged Spec Kit structural gate; extended actual-client Docker and previous supervised synthetic bridge regression passed. 36 existing PTB warnings. No production or personal service changes, no real messenger traffic or credentials. Remaining risk: whole-ledger rollback to a previously QUEUED row, simultaneous loss/rollback of both worker and gateway journals, loss of worker identity, or replay of a previously sent source event into a fresh worker cannot be made safe solely by submission_attempted. Require coordinated restore/continuity epoch and fail-closed recovery gate before live deployment. Automatic gateway/broker supervision, durable unified API cooldown, restricted real network/firewall, dynamic resources, live authorization, history/media parity and real tenant acceptance remain open. Next: coordinated recovery/restore continuity contract and trusted dependency supervision; no production guard lift.
