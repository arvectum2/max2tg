# P2.2b — protected Linux host storage contract and egress hardening

Base main dee0ad0 (merged PR #29). Canonical roadmap criteria unchanged. Read-only preflight; no authority to launch live SaaS.

## Proposed host layout

Use a dedicated Linux host, not the Mac mini personal service or Docker Desktop VM. Two separate LUKS-backed mapper filesystems (ext4 or xfs), mounted with nodev,nosuid,noexec, root-owned private mount roots. Suggested roots: /srv/max2tg/data and /srv/max2tg/backup. Below the first, create separately permissioned registry, per-capsule state and encrypted credential directories. Only the exact role paths may be bound into containers, with credentials read-only. Keep source and restored plaintext delivery snapshots only on protected storage; encrypted archives on separate backup storage. Use a dedicated root-owned private tmpfs at /run/max2tg-keys, no active swap, separate read-only key subdirectories per worker and gateway; a trusted host provisioner obtains scoped keys from independent protected custody, not a key file in source, logs, environment variables or the same persistent volume. Exclude keys from backups. Disable core dumps and hibernation, protect crash logs and review Docker storage, mount namespaces, snapshots and privileged host access. The recovery anchor and the durable copies of required keys must be retained independently of the restorable host and both data/backup volumes. Separate volumes alone do not prove independent retention or physical failure domains.

## Local evidence

Run on the trusted Linux host: `python3 scripts/saas-host-preflight.py --data /srv/max2tg/data --backup /srv/max2tg/backup --keys /run/max2tg-keys`. It reads actual /proc/self/mountinfo, path ownership, filesystem device numbers, /sys/dev/block/.../dm/uuid and /proc/swaps. It rejects overlapping/noncanonical paths, symlinks, nonprivate roots, ambiguous, aliased, nested or subroot mounts, absent mount restrictions, mismatched device numbers, non-LUKS mapper identifiers, duplicate LUKS identity, wrong filesystem and active/unverified swap. A PASS is limited to local storage observations. A mapper UUID is not cryptographic attestation of the mapping or host security; trusted operator must independently check the crypt target/cipher, storage/key lifecycle and actual container mounts. No change to system, disks, firewall, accounts or network. Exit 1 on local refusal; exit 0 on local checks only, with live_launch_authorized=false in either result. No JSON readiness override. No automatic enabling.

## Network and deployment gates

Workers and Telegram gateway must retain no direct external network; broker alone gets restricted HTTPS egress, per-role socket, dedicated DNS, exact destination hostname, numeric address pinning and firewall default deny. Further hardened DNS handling: reject IPv4/IPv6 family mismatch and special IPv6 ranges including translation addresses outside global-unicast 2000::/3, 2001::/23 and 3fff::/20. Policy is intentionally conservative; no DNS answer can be used until all answers are validated. CONNECT remains opaque TLS, so host firewall, peer identity and network namespace policies require separate on-host verification; no claim that the broker enforces SNI or host firewall. No direct inbound service needed for worker traffic.

Before real launch: (1) trusted operator validates local storage, actual encrypted mapping and role mounts, no swap/dumps; (2) independent key/anchor retention and restore rehearsal; (3) restrict live egress with positive/negative tests from each runtime namespace, DNS and host firewall verification; (4) deploy only pinned reviewed runtime and enforce restore/start gate, provisioning locks and recovery orchestration at actual entrypoint; (5) separate test bot, two independent MAX accounts and private forums for live acceptance. No personal account fault injection. No live guard lift. PostgreSQL, public onboarding, billing and beta hosting remain later roadmap work.
