# P2.2b — offline container lifecycle supervisor

Dependent on PR #11 (b0851a9). Synthetic development only; P2.2b remains open.

`OfflineContainerSupervisor` reconciles explicit desired state against Docker inspection. Uses a private persistent registry and exclusive flock, an immutable pinned image ID, per-session volume specifications and persistent owner labels. Only separately preprovisioned disposable volumes with the expected owner label and local driver are accepted. Volume overlap and foreign container identity/policy are rejected. No tenant-controlled commands, network, live secrets, production deployment or Docker socket mounts. The command is hardcoded to the synthetic fixture. Existing containers are checked for their immutable identity, image, mounts and selected runtime controls before start/stop. No automatic deletion or replacement of missing known containers. No forced restart on stale health or ambiguous daemon error. The host Docker control path remains privileged and trusted.

Every attempted create/start records a durable attempt before issuing the command. Exponential backoff; max four attempts (initial launch plus three retries). After exhaustion, quarantine requires explicit off/on. Restarting the supervisor retains the counter and container identity. Successful process health is not proof of MAX authorization or message delivery. Docker health probe checks synthetic heartbeat only. Non-root 65532, read-only root and secret mounts, no network, dropped capabilities, no-new-privileges, 256 MiB RAM, 0.5 CPU, 64 PIDs, bounded logs. Explicit desired=False stops only its own verified container; close hands off without stopping others. No data volume deletion by supervisor.

Two deterministic tests verify persistent crash budget/quarantine, foreign identity and volume reuse rejection, and duplicate supervisor lock. Real Docker Linux smoke creates six disposable volumes and two worker containers; both health checks succeed, one fixture intentionally exits, supervisor observes BACKOFF, closes/reopens, restarts same container once, other worker remains running with one start. Each stopped independently, volumes preserved until test-owned cleanup; no labeled resources left. 819 local tests, targeted Ruff, preflight and Spec Kit structural gate passed; 33 existing PTB warnings. CI adds the supervisor smoke alongside the existing synthetic message-delivery container test. Host script imports without external Python packages. No real accounts or personal service modified.

Limitations: lifecycle smoke uses a standalone synthetic heartbeat fixture, not the actual MAX client/runtime. Existing separate gateway/worker delivery test does not yet prove supervised recovery end-to-end. Explicit trusted preparation of volumes/ACL/keys/secret and registry activation are still separate operations; no automatic onboarding, live orchestration, restricted real outbound network, secret encryption/rotation, storage quota or actual field acceptance. Next: connect supervised lifecycle to isolated shared runtime using synthetic transports and durable recovery, then review a separately authorized real-account deployment design. Do not lift existing production supervisor guard.
