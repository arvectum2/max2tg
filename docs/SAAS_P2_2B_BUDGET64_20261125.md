# P2.2b — virtual-clock shared-budget capacity boundary

Base 9d09f23 (PR #43; fresh image CI still running at last check). Canonical acceptance unchanged. No runtime, API rate, lease TTL, verification concurrency or personal configuration changes. `python -m tests.virtual_budget_load` executes seven bounded synthetic scenarios using actual CapsuleRegistry, SharedOnboarding, ForumGuard, TelegramBudget, BudgetedBot and TelegramEgress. Virtual asyncio selector advances time only when no ready I/O and timer wait requested; real asyncio sleeps/timeouts use the same virtual loop clock. Shared limit 20 starts/s, five calls per check, TTL 30s, due 21s, four checks per wave, same 0.2s verification and 16-item serial egress rounds/0.05s progress or 1s idle sleeps. Approximate the existing lifecycle/drain exclusion with a shared lock; no IPC, reverse delivery, TLS, real network, host scheduling or SQLite execution duration modeled. Fixed synthetic response latency except empty 20s polling. SQLite real wall timestamps used for row ordering; random provisioned session IDs affect tie order, so exact figures vary slightly. Synthetic verified recipient and message keys checked at every invocation, guard must allow at call start; no duplicate invocation. Start spacing >=0.05s across all groups. Fault injects one poll RetryAfter(12) after 60s load, asserts no new starts strictly within cooldown and persisted deadline. Not proof of real API performance, continuous lease coverage or a real 64-container test.

Load starts only after all leases simultaneously valid (60s warmup limit). 120 virtual seconds evenly spaced offered outbound messages, round-robin sessions, then up to 90s to drain. Sample leases and pending queue every 0.1s. p95 measured from admission to synthetic send invocation, not receipt, not end-to-end. 150ms case drained after another 63.6s; repeat observed 64.6s and p95 58.75s. Serial send alone has ideal ceiling 6.67/s at 150ms, below 8/s offered even without pacing. Slow verification waves also limit lease coverage: 16 waves of 4 checks, each requires five serial awaited calls per forum, 350ms*5*16=28s before pacing/0.2s inter-wave/lock overhead. This explains why all-ready warmup fails, not a justification to extend TTL or skip checks. At 250ms load 3/s, occasional holds prevent unsafe delivery but all-ready acceptance fails; at 40ms load 8/s check cadence is stretched, though no sampled expiration. Cooldown properly holds affected sessions then all 360 messages eventually confirmed, no early starts. Virtual results are optimistic for real network/storage overhead. Two regression tests check fast/slow/cooldown and warmup refusal using robust inequalities, not exact random tie order. 944 full tests pass, 48 PTB deprecation warnings (3 additional from injected RetryAfter), targeted Ruff, preflight and structural Spec Kit pass.

Decision: do not escalate to 64 physical sessions yet. Next experiment: bounded rolling verification scheduler with deadline-aware admission and explicit lease margin observations; compare 64 at 250/350ms with unchanged five calls, TTL and shared 20/s budget. Separately characterize serial sender ceiling at offered load below/above service rate before considering bounded cross-tenant sends, preserve same-tenant order and UNKNOWN. If shared-bot envelope remains insufficient, establish measured per-bot safe admission cap and consider independently provisioned bot/tenant partitions with distinct credentials and ownership, not bypassing external rate limits.
