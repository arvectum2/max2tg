# P2.2b — weighted API admission and bounded cross-session sending

Base 6ee244e (PR #45). Original roadmap and acceptance unchanged. No personal deployment, production scheduling configuration, protected skills changes or real API calls. A test-only WeightedBudget arbitrates admission to the actual TelegramBudget using work-conserving weighted slots for verification and send waiters, with priority for the single polling caller. Weights verify/send 2:3 at 32, 3:2 at 48, 4:1 at 64. These are experimental static preferences, not guaranteed per-class rates or deadlines. One grant held until actual method invocation begins (or pre-call denial/cancellation); global pacing (20/s), durable RetryAfter, pre-call route/lease guard and conservative uncertain-outcome semantics remain in actual TelegramBudget. Rolling scheduler eight verification tasks (five serial reads, TTL30, due21, timeout8 unchanged) paired with at most four cross-session sends. No per-session rate-limit model; no claim about real Telegram policy or allowed commercial capacity.

Optional actual TelegramEgress.drain(concurrency=1..4) defaults to 1, existing runtime does not opt in. Parallel branch requires scoped ledger, BudgetedBot and authorization callback; exclusive ledger lock held across batch, fair selection grouped by session, one task per session with sequential awaits and global semaphore; stop group on QUEUED. Existing CAS, pre-call recheck and UNKNOWN transitions reused without change. Cancel/await all batch tasks before releasing lock. UNKNOWN never automatically replayed; invocation order within a session is preserved in a batch, ambiguous remote effects cannot be guaranteed ordered. This is not a new production gateway configuration or lifecycle integration. Test virtual sender checks exact owner/topic and increasing sequence per forum, no overlap within forum, no duplicate starts, global start spacing >=50ms, durable terminal totals, cooldown and no early starts. A cancellation test proves another tenant can complete ordered sends while first is blocked, canceled claimed send becomes UNKNOWN, unsent successor remains QUEUED and uncertain message is never replayed. Unit test checks weighted admission cancellation, local pre-call denial, pacing and cooldown. The real-time fixture/host lifecycle, network, HTTP pool and per-forum throttling are not modeled by virtual clock. Experimental selector uses real SQLite timestamps and random session identifiers for tie breaks; repeated observed results similar but not a statistical guarantee.

Reproduce `python -m tests.virtual_budget_load --balanced`. 120 virtual seconds of arrivals and bounded drain, fixed API latency except empty 20s polling. p95 from admission to invocation, not end-to-end. Representative repeat:

Cannot promise fixed all-ready or throughput at this load. 48/8/s exhibited sampled readiness loss (min40), so not accepted as an operating envelope. At 64/350ms/3/s all-ready warmup 16.4s, max three simultaneous sends, versus wave4 warmup failure; at 32/150ms/8/s baseline wave4 queue304 and p95 52.95s versus queue5 and p95 0.70s. At 48/350ms/3/s baseline p95 14.75s versus 0.50s. Not a same-seed causal decomposition: rolling scheduling, concurrency and weights changed together; baseline prior representative runs. Cooldown test holds expired leases and resumes after cooldown, no unauthorized/early invocations. 951 full tests, 54 existing/injected PTB deprecation warnings, targeted Ruff, runtime preflight and structural Spec Kit gate passed. Initial unused-import lint failure corrected and reverified. No physical 64-container run or real accounts yet.

Decision: retain optional parallel primitive and experimental weighted arbiter, do not enable in live or default runtime. Next: isolate integration behind trusted opt-in composition; actual synthetic TLS 32-worker comparison including delayed API responses, bounded HTTP pool, channel lifecycle/revocation, RetryAfter, concurrent cancellation and exact receipts. Measure queue and lease margin before proposing conservative per-bot admission envelope (32 is a tested cohort, not a production cap). No expansion to 64 physical workers until these gates pass. Protected host and independent real account acceptance remain open.
