# P2.2b — bounded fair managed gateway drain

Base 3d296cd (PR #35); original roadmap and acceptance unchanged. Previous 16-tenant burst: 640 confirmed, 48.840 s, TG→MAX p95 22.692 s and MAX→TG p95 44.503 s. Inspection found serial ingress IPC and a common drain lock held across 100 ingress + 50 egress items; one second delay between rounds. Changes isolated to managed shared gateway behavior, plus additive indexes and compare-and-swap terminal guards on central ingress. Personal runtime not changed. No live traffic.

Managed drain uses 32 ingress and 16 egress maximum per round, 4 concurrent independent ingress session groups, with the existing per-session lock and sequential update IDs per group. A definitely unavailable worker stops its group at that item; other groups continue. SQL window ranks each session's pending rows by original order, selects earliest rank first and ties by original global order. Egress retains one serial sender and shared 20 starts/s API budget, with tenant-interleaved selection. Lifecycle lock released after each round; next round 50 ms when progress made, 1 s otherwise. This is bounded selection/concurrency, not a hard real-time latency guarantee; a stalled network call can delay its batch and more tenants than slots with unavailable oldest items may require further scheduling work. Fair query cost grows with queued rows. No parallel Bot API mutations or change to RetryAfter policy. Ingress final state transitions compare against INFLIGHT, never overwrite a competing UNKNOWN recovery marker. Existing route/lease checks at dispatch retained. Cancellation marks in-flight uncertain; pending remains pending. No arbitrary replay or new production enablement.

Focused tests demonstrate an unavailable session cannot block other workers, per-session ordering, fair egress order and held-session exclusion, late ACK cannot overwrite UNKNOWN. 923 full tests, 45 existing PTB warnings, targeted Ruff, runtime preflight and Spec Kit structural checks pass. Worker receipt repair still scans all SENT rows and uses bounded JSON map; not modified in this experiment so performance attribution is limited to this scheduling candidate. Separate next experiment needed for incremental receipt index and 1000-entry eviction case.
