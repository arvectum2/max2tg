# P2.2b / P0.5b — operator staging inventory (first operational slice)

Base b3517bf (PR #51). Original roadmap and acceptance criteria remain unchanged. This is preparation of a persistent held deployment, not runnable SaaS or an authorization to launch. Reuses the canonical held placement builder and stopped-container verifier. No live credentials, network activation, container start/stop/restart/removal, provisioning of accounts, or unrelated service changes. No protected skills modified.

Trusted operator provides a new private canonical operator directory, separate existing private bind directories under data/key roots, separate backup root, explicit unique tenant IDs and a locally pinned image ID. Example (replace placeholders with separately provisioned paths/identities):

```sh
python -m app.operator_stage --state /srv/m2tg-operator prepare \
  --deployment <24-hex> --image sha256:<64-hex> \
  --data /srv/m2tg-data --keys /run/m2tg-keys --backup /srv/m2tg-backup \
  --sid <24-hex> --sid <24-hex>
python -m app.operator_stage --state /srv/m2tg-operator status
```

The command validates the generated plan and exact existing bind sources; records device/inode/owner, Docker daemon identity, local image ID and plan digest; uses owner-only lock and durable atomic manifest publication. `compose.json` and `stage.json` are private metadata; plan regenerated and checked on reopen. Pre-existing names refused. Create each held role without build/pull/recreate (no Compose dependencies in generated plan), record exact verified full container ID after each confirmed create. Final HELD requires exact complete inventory and actual created-state isolation: network none, read-only root, explicit held command, exact role mounts, limits, capabilities, log limits and no ports. Repeating identical prepare only verifies existing inventory. Different configuration, missing/replaced/running container, changed daemon, mount or bind identity fails closed. Incomplete/ambiguous create records BLOCKED or leaves non-HELD manifest, no automatic retry, adoption or deletion; operator must review actual resources. CLI nonzero on failure. No claim of cryptographically authenticated inventory against a privileged host attacker. Trusted operator must exclude concurrent external Docker and filesystem changes; device/inode checks are observations, not immutable mount locks. The current per-role verification is intended for small staging cohorts and has quadratic inspection cost; scale separately before using for large deployments. Local storage encryption, firewall, independent backup/key/anchor custody and actual real-account acceptance remain distinct gates. Mac Docker Desktop prefix normalization only for exact known bind targets. No root/OS/Docker daemon configuration changes.
