# P2.2b — supervised actual-client bridge and broker outage recovery

Base: main 9625cc2 (merged PR #19). Offline candidate only; P2.2b remains open.

The offline supervisor has an additional immutable allowlisted `proxy-bridge` fixture, requiring a distinct labeled network channel volume. It mounts this read-only, verifies the extra mount before operating the container and rejects cross-tenant volume reuse. Existing heartbeat/bridge fixtures remain compatible. No arbitrary command or live network activation. All runtime containers use network=none, non-root UID and existing restrictions. The fixture starts a separate synthetic TLS broker and gateway, then launches two workers through the supervisor driven by lifecycle reconciliation. Broker has only network channel volumes and a disposable test certificate; no registry, worker state or MAX secret mounts. Workers have separate state, IPC, read-only secret and read-only network channel mounts. Gateway has registry, two IPC channels and its own network channel; fixture-only control/evidence files share the gateway network volume. Synthetic MAX and Telegram TLS servers bind only broker loopback. MAX actual binary handshake/auth/send/DISPATCH and actual PTB Bot API are used by the existing isolated bridge runtimes. No direct network path.

Actual Mac mini Docker evidence: four runtime containers and ten disposable volumes. Initial two MAX-to-Telegram and two Telegram-to-MAX confirmed deliveries; broker closes A's dedicated listener and existing stream. A becomes unauthorized while B stays authorized. A's next Telegram update remains RECEIVED; B's next is ACKED. Reopening A's listener restores MAX authorization and drains A's pending update. Repeated synthetic MAX DISPATCH of the same ID after reconnect does not resend the already confirmed Telegram message. Final phase synthetic MAX records one send side effect and closes the WebSocket before receipt. Gateway and worker both retain UNKNOWN, A reconnects, no automatic replay. Exact synthetic-server evidence: four confirmed Telegram-to-MAX sends, one uncertain MAX send, two confirmed MAX-to-Telegram sends. Both container IDs and start budgets unchanged (one start each). Both stopped independently; broker/gateway exit cleanly and all labeled disposable resources removed.

868 tests passed; targeted Ruff, runtime preflight, unchanged Spec Kit structural gate and existing supervised bridge regression smoke passed. New real Docker synthetic test passed and added to CI. 36 existing PTB deprecation warnings. No personal bridge modifications, production activation or live messenger calls. ARC rejected one oversized command before execution; split into valid commands and completed. No real account/secret use. Chosen test-only reconnect interval 0.5 seconds is not production policy.

Limitations: broker and gateway lifecycle are driven by the trusted test harness, not by a production supervisor; the tested outage is one MAX broker channel, not a full broker/gateway crash or Telegram outage. The gateway fixture has a simple NetworkError catch, not a production retry scheduler. Positive process heartbeat is distinct from MAX authorization. No history gap catch-up, media parity, live-network firewall, production DNS/TLS evidence, user-facing authorization, durable unified API cooldown, secret rotation/encryption, dynamic provisioning or real multi-account acceptance. Next: review the remaining delivery-ledger continuity risks and implement durable coordinated dependency recovery (gateway/broker loss, rate limits and UNKNOWN retention), then prepare an explicit restricted live-network deployment plan. Keep production shared mode disabled until separately authorized field acceptance.
