# P2.2b — unified managed Telegram API pacing and durable RetryAfter

Base main 795e8d3 (merged PR #25). Offline managed gateway only; canonical acceptance remains unchanged.

`TelegramBudget` paces starts of all currently supported managed gateway calls through one shared explicit Bot wrapper: getMe (including isolated transport initialization), getChat, getChatMember, getChatMemberCount, getUpdates, sendMessage, createForumTopic. Default 20 starts/s without burst is a provisional local engineering limit, not a Telegram quota guarantee. ForumGuard uses the same budget instead of an independent limiter in managed mode. The existing standalone verification limiter and personal runtime are unchanged. Numeric or timedelta RetryAfter updates a FULL-synchronous central registry deadline (also included in its coordinated database backup); monotonic deadline guards the running process, the persisted wall-clock deadline survives process restart. Pending calls are rejected before network invocation during cooldown, in-flight calls cannot be recalled. The isolated Telegram initialization waits out cooldown instead of attempting getMe during it; polling keeps offset unchanged on deferred/RetryAfter. No hidden retries of mutations. A DB write error latches budget failure in the current process. Clock trust and independent durable storage remain prerequisites.

Only a local ApiDeferred before calling the API permits a SENDING egress claim to return to QUEUED, or deletion of a newly inserted topic creation intent. The wrapper rechecks current routing and membership authorization immediately after pacing, before invocation. Actual API exception, including RetryAfter after invocation, conservatively quarantines the attempted send/topic creation as UNKNOWN; subsequent unattempted operations stay queued/deferred. Existing UNKNOWN is never replayed. This intentionally sacrifices availability under ambiguous outcomes. Direct injected managed runtime startup refuses during persisted cooldown; isolated client startup waits. Trusted operator still must serialize gateway initialization and provisioning; externally injected onboarding calls outside managed runtime are not yet covered by this budget.

Evidence: two new tests use a deterministic clock for all seven mixed operations, exact pacing, cooldown across reopened SQLite, polling offset retention, no call on local defer, revocation while pacing, actual RetryAfter -> UNKNOWN, queued continuation and topic creation after recovery. Extended actual-client four-container synthetic TLS test returns an HTTP 429 with RetryAfter=8 to real PTB getUpdates; after persisted cooldown is observed, hard-kills gateway and restarts via dependency controller. Synthetic broker records zero premature Bot API requests; recovery confirms existing 4 ACKED + 2 SENT + 1 UNKNOWN, exact server-side side effects and unchanged workers. Previous supervised bridge smoke also passed. 882 tests passed, 45 PTB deprecation warnings (9 from new exercises), targeted Ruff, runtime preflight and original Spec Kit structural gate passed. No live accounts/network/production changes.

Limits: single trusted gateway, clock continuity assumed; no shared distributed rate budget, per-chat quota or sustained real API capacity evidence. Budget covers currently supported managed gateway methods, not arbitrary future Bot methods or separate provisioning operator APIs. A process/storage crash before RetryAfter persistence can lose evidence; in-flight calls and arbitrary storage rollback cannot be recalled. No production deployment, live acceptance or full automatic host daemon. Next: trusted provisioning/runtime write fence and independently retained recovery continuity marker, then secure deployment review, protected secret retention and real isolated-account acceptance. Keep shared production disabled.
