# P2.2b — restored cohort launch gate and provisioning fence

Base 3a75012 (PR #26). Original roadmap and acceptance criteria unchanged; offline only.

SharedOnboarding now holds a cooperative shared filesystem lock across registration mutations, forum verification awaits, provisioning confirmation, activation, key creation and revocation. Existing stopped-runtime backup takes its exclusive counterpart in addition to the existing gateway and worker locks. Concurrent registration and backup refuse rather than race. RuntimeLock also rejects hard-linked lock files. This fence covers SharedOnboarding, not arbitrary direct registry/SQL writes; trusted operator still stops other writers and serializes provisioning.

`launch_verified_restore` is an explicit trusted async orchestration path for a freshly reconstructed restored cohort, not ordinary restart of intact volumes. Independent backup lock remains held throughout verification and launch callback. Before launch it acquires existing runtime/provisioning locks, validates exact external tenant membership and all 11 delivery-state file digests (two-worker case), rejects SQLite WAL/SHM/journal sidecars, verifies owner/forum ACL, retained central/local IPC key equality, private paths and separately retained per-worker MAX secret identity. It never regenerates missing keys or loads MAX credentials into the gateway. It fsyncs the independent dirty anchor BEFORE handing off to the trusted runtime launch. Failure after that point leaves dirty; no automatic clean reset/relaunch from backup. Runtime locks are released for the handoff, so exclusive host control of launch and low-level writers remains a prerequisite. No claim of protection against an operator bypassing this explicit path, simultaneous rollback of anchor and data, hostile filesystem or ordinary runtime restart. No secret encryption implemented here; private file permission checks and separate retention are not encryption.

Integration test extends actual stopped-runtime backup test: two reconstructed isolated worker state folders and gateway registry, separately retained synthetic keys/secrets. Rejects wrong key, unexpected WAL and modified SQLite before invoking start. Starts actual gateway/worker classes with synthetic messenger boundaries only after dirty anchor is observed, checks retained two ACKED and two SENT receipts, replays identical synthetic MAX events without extra Telegram sends, refuses a second restored launch with dirty anchor. Backup refuses while provisioning lock held. Separate test holds actual forum verification in flight and proves exclusive backup fence unavailable; exclusive fence blocks registration/verification/revocation. 883 tests passed (45 PTB warnings), targeted Ruff, runtime preflight and Spec Kit structural gate; previous Docker bridge regression passed. No real account, production data, or personal bridge change.

Remaining: enforce trusted restore entrypoint at deployment boundary, secure independent anchor retention, encrypted secret/backup storage with key rotation and recovery testing, complete restricted live network and separate-account acceptance. No P2.2b/P2.2c closure or production guard lift. Next: encrypted secret/backup retention design and tested key lifecycle, without migrating personal credentials or enabling live accounts.
