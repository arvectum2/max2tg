# P2.2b — bounded forum verification scheduler

Base: 7bdf895 (PR #16, merged). Offline candidate only. P2.2b remains open.

ForumGuard now processes one bounded wave of up to four due forums, oldest scheduled deadline first with deterministic tie-break. Verification reads are paced globally per gateway process, default 20 call starts per second with no burst allowance. Five reads per complete verification. Positive membership evidence expires after 30 seconds from check start; recheck is due after 21 seconds. An expired or invalidated lease never becomes valid by overload, skipped checks or a stale in-flight result. A concurrent membership event invalidates the generation, preventing an older response from restoring a lease. Explicit policy violations still revoke.

Telegram RetryAfter (numeric seconds or timedelta) suspends verification reads across the gateway for at least the indicated duration; already in-flight requests cannot be recalled. Other failures use per-session exponential backoff 5/10/20/40/60 seconds, capped at 60. Success clears the failure counter. Valid leases for unaffected forums expire normally; verification outages retain unattempted queues. No automatic resend of UNKNOWN. The limiter is process-local and covers only verification reads, not all bot operations or multiple gateway replicas. Cooldown is not persisted across restart; real deployment must coordinate API budgets across operations and preserve cooldown. Limits are provisional engineering choices, not Telegram's guaranteed quotas.

Managed gateway run loop separates verification from polling and draining; network checks no longer hold the delivery lock. Listener changes remain serialized with delivery. The managed start checks at most one wave; other sessions remain unready until verified. The synthetic fixture still exercises the same gateway/worker code under Docker. Load beyond verification capacity deliberately leaves some sessions held; no extended trust or automatic capacity claim.

Evidence: 100 synthetic forums, 500 verification reads, 24.95 seconds virtual elapsed between first and last call, spacing at least 0.05s, observed peak two in-flight reads (configured max four). Every forum obtained an initial lease; after simulated expiry none remained authorized; next wave verified only four. This is deterministic clock simulation, not 100 live sessions or a sustained production throughput benchmark. Tests also cover RetryAfter cooldown despite membership invalidation, exponential backoff and recovery, event arriving during an in-flight check. Initial test assertion compared floating-point values exactly; switched to approximate comparison, reran. 833 tests passed, 36 PTB deprecation warnings (including three RetryAfter exercise warnings); targeted Ruff, runtime preflight, original Spec Kit structural gate and supervised Docker smoke passed. No real Telegram traffic, secrets, personal bridge or deployment changes.

Remaining: unified Bot API rate budget for polling, sends, provisioning and verification; durable cooldown and real workload/latency measurement; controlled network access for workers, actual MAX authorization, dynamic volume provisioning, secret rotation/encryption, history/media parity and isolated live acceptance. Next: controlled live-network architecture and offline egress policy tests, without enabling real accounts or lifting the existing production guard.
