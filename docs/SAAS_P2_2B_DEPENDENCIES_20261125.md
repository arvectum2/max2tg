# P2.2b — persistent offline dependency supervision

Base main 231f4fa (merged PR #24). Original roadmap acceptance unchanged. Offline only.

DependencySupervisor registers two explicitly pre-created synthetic containers (broker and gateway) with pinned identity, inspected configuration, role-specific mounts and owner-labeled local volumes. It cannot create, replace or delete dependencies. The controller checks configuration before acting, including network=none, non-root user, read-only root, capabilities and resource bounds. Docker Desktop's exact host_mnt representation is accepted for the expected bind source; mount ordering is normalized and selected stable host configuration fields are fingerprinted. No arbitrary commands. Desired state, attempt counter and backoff are durable in a separately locked SQLite database. Broker must be healthy before a stopped gateway starts; running unhealthy processes are observed, not force-killed. Missing or substituted containers are not recreated. Initial start counts toward four attempts; only explicit off/on resets the budget. Health probes use fresh fixture heartbeat and process start time, not historical log lines. This is fixture-level readiness, not proof of upstream authorization.

Actual four-container synthetic TLS smoke: both dependencies pre-created stopped and started by controller in order; two MAX workers deliver both ways. A channel outage leaves a pending update while B delivers. Hard-kill gateway and broker at known durable boundary; both workers lose authorization. Reopen dependency controller with same SQLite database and retained attempt count, resume ticks; broker starts and becomes healthy, gateway restarts and reconciles queued delivery. Both dependency container IDs retained, attempts two each; both worker IDs unchanged, attempts one each. Final six confirmed deliveries and one UNKNOWN, exactly one ambiguous send, no duplicate. Disposable resources removed. Initial Docker trials exposed host_mnt path representation and unstable inspect fingerprint across start; corrected exact-path validation and stable configuration fingerprint, reran successfully. Two deterministic tests verify backoff, handoff, four-attempt quarantine, dependency ordering, missing/substituted/changed identity, no force-kill of unhealthy container. 880 tests passed, targeted Ruff, runtime preflight and original Spec Kit structural gate passed (36 existing PTB warnings). No live messenger traffic or production changes.

Limits: trusted synthetic harness still drives ticks and pre-creates dependencies, no persistent host daemon or automatic recovery from missing volumes/containers. Broker/gateway readiness probe is fixture heartbeat; no arbitrary in-flight gateway crash guarantee, no recovery of hung but running components, no real network policy or real account acceptance. Code binds are trusted mutable host source, not immutable content; selected stable host config fingerprint is not comprehensive sandbox attestation. Retry budget is deliberately conservative and needs operator reset after exhaustion. Production write fence and coordinated restore, durable unified API cooldown, encrypted secrets/backups and dynamic resource provisioning remain open. Next: unified Telegram API pacing/cooldown persisted across gateway restart; synthetic mixed-operation and RetryAfter restart acceptance. Keep shared production mode disabled.
